## Issue A-1: データ型と保存キーを定義する

### タイトル案

`Phase 1: データ型と localStorage 保存キーを定義する`

### 本文案

```md
## 背景

ルーレットアプリの初期版では、候補リスト、抽選済み状態、抽選済み候補を除外する設定をブラウザの `localStorage` に保存する。
同名候補を許可するため、候補は表示名ではなく内部 ID で管理する必要がある。

現時点では要件と詳細設計は整理済みだが、実装の土台となる型定義、保存キー、保存フォーマットがまだコード上に存在しない。
この Issue では、以降の UI 実装と抽選ロジック実装の前提になるデータモデルを先に揃える。

## 対応要件

- FR-014 同一名称の候補は名称ではなく内部 ID で区別する
- FR-015 ページ再読み込み後も候補リスト、抽選済み状態、除外設定を保持する
- NFR-007 状態保存には `localStorage` を利用する
- NFR-008 保存対象は候補リスト、抽選済み状態、抽選済み除外設定に限定する

## 作業内容

- `RouletteCandidate` 型を定義する
- `RouletteSettings` 型を定義する
- `RouletteState` 型を定義する
- `RouletteStorageData` 型を定義する
- `DrawAvailability` 型を定義する
- `DEFAULT_SETTINGS` と `DEFAULT_STATE` を定義する
- `STORAGE_KEYS.rouletteState` を定数化する
- 候補 ID 生成関数を追加する

## 実装メモ

- 候補は `id`, `name`, `drawn`, `createdAt`, `updatedAt` を持つ
- 設定は `excludeDrawnCandidates` を持つ
- 保存データは `version: 1` を含む 1 オブジェクトで保持する
- 保存キーは `roulette.state.v1` とする
- 候補 ID は表示名から作らない
- 可能なら `crypto.randomUUID()` を優先する

## 完了条件

- 候補型と設定型がコードから参照できる
- `localStorage` 用の保存キーが定数化されている
- 既定値が 1 か所にまとまっている
- 同名候補でも別 ID を生成できる
- 今後のストレージ読み書き実装で再利用できる状態になっている

## レビュー観点

- 候補識別に候補名を使っていないか
- 保存キーが文字列リテラルで散在していないか
- 保存フォーマットにバージョンが含まれているか
- 初期値が UI 実装側に重複していないか

## チェックリスト

- [ ] 型定義を追加した
- [ ] 既定値を追加した
- [ ] 保存キーを定数化した
- [ ] ID 生成関数を追加した
- [ ] 参照元ドキュメントとの不整合がないことを確認した
```

## Issue A-2: 抽選ロジックを UI から分離して実装する

### タイトル案

`Phase 1: 抽選ロジックを純粋関数として分離する`

### 本文案

```md
## 背景

ルーレットアプリでは、抽選対象候補の絞り込み、抽選可能判定、ランダム選択、抽選済み更新を扱う必要がある。
これらの分岐を UI 側に直接書くと、候補不足判定や抽選済み除外設定の分岐が散らばり、保守しづらくなる。

この Issue では、抽選ロジックを純粋関数として切り出し、UI から独立してテスト可能な形に整える。

## 対応要件

- FR-005 候補が2件以上ある場合に抽選を開始できる
- FR-006 抽選結果は抽選対象候補の中からランダムに1件選ばれる
- FR-009 抽選済み候補を次回抽選から除外するかどうかを設定できる
- FR-011 候補が不足している場合は抽選を実行せず、理由を表示する
- NFR-009 抽選ロジックと UI 表示を分離する
- NFR-010 抽選ロジックは単体テスト可能な純粋関数として切り出す

## 作業内容

- `getEligibleCandidates` を実装する
- `getDrawAvailability` を実装する
- `pickRandomCandidate` を実装する
- `markCandidateAsDrawn` を実装する
- 入力配列を破壊しない実装にする
- `randomValue` 注入でテストしやすい形にする

## 実装メモ

- `excludeDrawnCandidates === true` の場合は未抽選候補のみ対象にする
- `excludeDrawnCandidates === false` の場合は全候補を対象にする
- 候補総数 0 件は `NO_CANDIDATES`
- 抽選対象候補 0 件かつ総候補数 1 件以上は `ALL_DRAWN`
- 抽選対象候補 1 件は `NOT_ENOUGH_CANDIDATES`
- `pickRandomCandidate` は空配列で例外を投げる
- `markCandidateAsDrawn` は対象候補の `drawn` と `updatedAt` だけ更新する

## 完了条件

- UI から独立して呼べる抽選ロジック関数がある
- 候補不足判定と理由コードが統一されている
- 抽選済み除外設定の ON / OFF で候補絞り込みが切り替わる
- ランダム選択処理がテストしやすい形になっている
- 更新処理が不変データで返る

## レビュー観点

- 候補選定ロジックが UI イベント内に埋め込まれていないか
- `excludeDrawnCandidates` の分岐が複数箇所に散っていないか
- 空配列や境界値の扱いが曖昧でないか
- 候補更新で表示名ではなく ID を使っているか
- テストで乱数依存を外せる設計になっているか

## チェックリスト

- [ ] 抽選対象絞り込み関数を追加した
- [ ] 抽選可否判定関数を追加した
- [ ] ランダム選択関数を追加した
- [ ] 抽選済み更新関数を追加した
- [ ] 入力破壊がないことを確認した
- [ ] 単体テストしやすい関数設計になっていることを確認した
```
