## 1. 背景

GitHub 上で要件定義をレビューした結果、レビュー可能な要件定義書は未登録だった。
確認できた `README.md` はタイトルのみで、目的、対象範囲、機能要件、非機能要件、業務ルール、受入条件が記載されていなかった。

そのため、本ドキュメントはレビュー可能な初版ドラフトとして作成する。
内容は現時点の仮説を含むため、仕様確定前に関係者レビューを実施すること。

## 2. 目的

本アプリは、候補者または候補項目の中からランダムに1件を選出するルーレット機能を提供する。
利用者が直感的に候補を登録し、抽選を実行し、結果を確認できる状態を目指す。

## 3. スコープ

### 3.1 対象範囲

- 候補項目の登録、編集、削除
- ルーレットによるランダム抽選
- 抽選結果の表示
- 抽選済み候補の扱いの制御
- 候補リストのリセット
- 基本的なエラーハンドリング
- スマートフォンおよびPCでの利用

### 3.2 対象外

- ユーザー認証
- 外部サービス連携
- 決済機能
- 複数ユーザーによる同時編集
- 厳密な監査ログ
- 高度な統計分析

対象外項目は、今後必要性が確認された場合に別途 Issue または追加要件として管理する。

## 4. 想定ユーザー

| 区分 | 説明 |
| --- | --- |
| 一般利用者 | 候補を入力し、ルーレット抽選を実行するユーザー |
| 管理者 | 候補リストや抽選状態を整理するユーザー。現時点では一般利用者と同一でもよい |

## 5. 利用シナリオ

### 5.1 基本シナリオ

1. 利用者が候補項目を入力する。
2. 利用者が抽選開始ボタンを押す。
3. ルーレット演出が表示される。
4. 抽選結果が1件表示される。
5. 必要に応じて次の抽選を行う。

### 5.2 リセットシナリオ

1. 利用者が候補リストまたは抽選済み状態をリセットする。
2. アプリは確認ダイアログを表示する。
3. 利用者が確認すると、状態が初期化される。

| NFR-003 | 操作ボタン、入力欄、結果表示は視認しやすいサイズにする | 必須 |

| NFR-008 | 将来の機能追加に備え、抽選ロジックと UI 表示を分離する | 推奨 |

## 8. 業務ルール・仕様ルール

### 8.1 抽選対象

- 空の候補は抽選対象に含めない。
- 削除済み候補は抽選対象に含めない。
- 抽選済み候補を除外する仕様を採用する場合、全候補が抽選済みになった時点で再抽選不可とするか、自動リセットするかを決める必要がある。

### 8.2 ランダム性

- 初期実装では `Math.random()` 相当の疑似乱数でよい。
- 公平性や監査性が必要な用途では、別途乱数生成方式を見直す。

### 8.3 重複候補

- 同名候補を許可する場合、候補は名称ではなく内部 ID で管理する。
- 同名候補を禁止する場合、登録時に重複エラーを表示する。
- 現時点では仕様未確定のため、レビューで決定する。

## 9. 画面要件

### 9.1 メイン画面

- 候補入力欄
- 候補追加ボタン
- 候補一覧
- 抽選開始ボタン
- 抽選結果表示エリア
- リセットボタン

### 9.2 表示メッセージ

| 状況 | メッセージ例 |
| --- | --- |
| 候補が空 | 候補を入力してください |
| 候補不足 | 抽選には2件以上の候補が必要です |
| 抽選完了 | 結果: {候補名} |
| 全候補抽選済み | 抽選可能な候補がありません。リセットしてください |

## 10. 受入条件

| ID | 条件 |
| --- | --- |
| AC-001 | 候補を2件以上登録すると抽選を実行できる |
| AC-002 | 抽選結果は登録済み候補のいずれか1件である |
| AC-003 | 候補が0件または1件の場合、抽選は実行されずエラーが表示される |
| AC-004 | 空文字候補は登録できない |
| AC-005 | 候補削除後、削除済み候補は抽選結果に出ない |
| AC-006 | リセット操作により抽選状態を初期化できる |
| AC-007 | スマートフォン幅でも主要操作が画面内で完結する |
| AC-008 | 画面に表示する候補名に HTML やスクリプトが含まれても安全に表示される |
