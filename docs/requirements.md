# ルーレットアプリ 要件定義書

- ステータス: 正本 / Active Draft
- 作成日: 2026-05-15
- 最終更新日: 2026-05-18
- 対象リポジトリ: `tanaka03-sketch/roulette`
- 正本ファイル: `docs/requirements.md`

## 1. 目的

本アプリは、利用者が登録した候補項目の中からランダムに1件を選出するルーレット機能を提供する。

初期版では、認証やサーバー側状態管理を持たない、単一ユーザー向けのクライアント完結型アプリとして実装する。
候補登録、抽選、抽選済み管理、リセットをブラウザ上で直感的に行える状態を目指す。

## 2. スコープ

### 2.1 対象範囲

- 候補項目の登録、編集、削除
- 候補一覧の表示
- ルーレットによるランダム抽選
- 抽選結果の表示
- 抽選済み候補の管理
- 抽選済み候補を次回抽選から除外するかどうかの切り替え
- 候補リストおよび抽選状態のリセット
- ブラウザ再読み込み後の状態保持
- 基本的な入力エラー表示
- PC およびスマートフォンでの利用
- GitHub Actions による基本的な自動検証

### 2.2 対象外

初期版では以下を対象外とする。

- ユーザー認証
- 管理画面の分離
- サーバー側データ保存
- 外部サービス連携
- 決済機能
- 複数ユーザーによる同時編集
- 厳密な監査ログ
- 高度な統計分析
- 複数ルーレットの作成・管理
- 抽選履歴の永続保存

対象外項目は、必要性が確認された場合に別途 Issue または追加要件として管理する。

## 3. 想定ユーザー

| 区分 | 説明 |
| --- | --- |
| 一般利用者 | 候補を入力し、ルーレット抽選を実行するユーザー |
| 管理者 | 初期版では一般利用者と同一。専用管理画面や認証は設けない |

## 4. 利用シナリオ

### 4.1 初回利用

1. 利用者がアプリを開く。
2. 利用者が候補項目を2件以上入力する。
3. 利用者が抽選開始ボタンを押す。
4. アプリがルーレットまたは同等の抽選演出を表示する。
5. アプリが候補一覧の中から1件を抽選結果として表示する。
6. 抽選結果の候補を抽選済みとして扱う。

### 4.2 抽選済み候補を除外する場合

1. 利用者が「抽選済み候補を次回抽選から除外する」設定を有効にする。
2. 抽選済み候補は次回以降の抽選対象から外れる。
3. 全候補が抽選済みになった場合、アプリは抽選を実行せず、リセットを促す。

### 4.3 抽選済み候補を除外しない場合

1. 利用者が「抽選済み候補を次回抽選から除外する」設定を無効にする。
2. 抽選済み候補も次回以降の抽選対象に含める。
3. 抽選済み表示は履歴的な補助情報として扱う。

### 4.4 リセット

1. 利用者がリセットボタンを押す。
2. アプリは確認ダイアログを表示する。
3. 利用者が確認すると、抽選済み状態を初期化する。
4. 候補リスト全体を削除する操作を設ける場合は、抽選状態リセットとは別操作にする。

## 7. データ要件

### 7.1 候補データ

候補は名称ではなく内部 ID で管理する。

```ts
type RouletteCandidate = {
  id: string;
  name: string;
  drawn: boolean;
  createdAt: string;
  updatedAt: string;
};
```

### 7.2 設定データ

```ts
type RouletteSettings = {
  excludeDrawnCandidates: boolean;
};
```

### 7.3 保存先

- 保存先はブラウザの `localStorage` とする。
- 保存キー名は実装時に定数化する。
- サーバー保存やユーザー間共有は初期版では行わない。

## 8. 業務ルール・仕様ルール

### 8.1 抽選対象

- 空文字または空白のみの候補は登録できない。
- 120文字を超える候補名は登録・保存できない。
- 削除済み候補は抽選対象に含めない。
- `excludeDrawnCandidates` が `true` の場合、抽選済み候補は抽選対象に含めない。
- `excludeDrawnCandidates` が `false` の場合、抽選済み候補も抽選対象に含める。

### 8.2 候補数

- 抽選対象候補が0件の場合、抽選は実行しない。
- 抽選対象候補が1件の場合も、初期版では抽選を実行しない。
- 抽選を実行するには、抽選対象候補が2件以上必要とする。

### 8.3 全候補抽選済み時の扱い

- `excludeDrawnCandidates` が `true` で全候補が抽選済みの場合、抽選は実行しない。
- 自動リセットは行わない。
- 利用者にリセット操作を促すメッセージを表示する。

### 8.4 重複候補

- 同一名称の候補登録を許可する。
- 同一名称の候補は内部 ID で別候補として扱う。
- 表示上は同じ名称が複数行に並ぶ可能性を許容する。
- 同一名称の候補が複数ある場合でも、各候補を画面上で識別できる補助情報を表示する。
- 初期版では識別用の補助情報として登録順番号を表示する。
- 編集・削除操作のラベルにも同じ識別情報を含める。

### 8.5 ランダム性

- 初期版では `Math.random()` 相当の疑似乱数でよい。
- 暗号学的な公平性、監査性、改ざん耐性が必要な用途には使わない。
- 公平性や監査性が必要になった場合は、乱数生成方式とログ設計を別途見直す。

### 8.6 CI 運用

- CI では Node.js 環境をセットアップしたうえで、依存関係導入、テスト、ビルドを順に実行する。
- CI の依存関係導入は `npm ci` を用いる。
- `package-lock.json` をリポジトリで管理し、`actions/setup-node` の `cache: npm` と整合させる。

## 11. テスト観点

### 11.1 抽選ロジック

- 候補0件で抽選できないこと。
- 候補1件で抽選できないこと。
- 候補2件以上で抽選できること。
- 抽選結果が抽選対象候補に含まれること。
- 抽選済み除外設定が有効な場合、抽選済み候補が除外されること。
- 抽選済み除外設定が無効な場合、抽選済み候補が除外されないこと。
- 全候補抽選済み時に自動リセットされないこと。

### 11.2 候補管理

- 候補を追加できること。
- 候補を編集できること。
- 候補を削除できること。
- 空文字候補を追加できないこと。
- 空白のみの候補を追加できないこと。
- 120文字を超える候補名を追加・保存できないこと。
- 同一名称の候補を複数登録できること。
- 同一名称候補が内部 ID で区別されること。
- 同一名称候補が画面上の識別情報でも区別できること。

### 11.3 状態保存

- 再読み込み後も候補リストが復元されること。
- 再読み込み後も抽選済み状態が復元されること。
- 再読み込み後も抽選済み除外設定が復元されること。
- 不正な `localStorage` データがある場合、アプリが壊れず初期化またはエラー表示できること。
- `localStorage` 自体にアクセスできない環境でも、アプリが初期表示で停止しないこと。

### 11.4 UI / セキュリティ

- スマートフォン幅で主要操作が利用できること。
- 候補名に `<script>alert(1)</script>` を入力してもスクリプトとして実行されないこと。
- 長い候補名を入力してもレイアウトが大きく崩れないこと。
- 同名候補の編集・削除ボタンが識別情報付きで操作できること。
- リセットおよび全削除操作で確認ダイアログが表示されること。
- 抽選中は候補や設定を変更できず、結果表示と一覧状態が競合しないこと。

### 11.5 CI / 開発品質

- `main` への push で CI が起動すること。
- pull request でも CI が起動すること。
- CI が依存関係導入の段階で停止せず、テストとビルドまで到達すること。
- ロックファイル運用と CI 設定が矛盾しないこと。
- CI 失敗時に、GitHub Actions 上で失敗段階を特定できること。
