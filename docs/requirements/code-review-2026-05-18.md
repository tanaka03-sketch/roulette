  - `localStorage` の保存・読込・初期化を担当する

### 主な振る舞い

- 候補は `id` ベースで管理し、同名候補を許可する
- 抽選済み候補を次回抽選から除外する設定を持つ
- 状態は `localStorage` に保存する
- 抽選中は 900ms の演出待ちをはさみ、その間は操作をロックする

## 2. 指摘事項

### 2-1. Medium: 同名候補を見分ける UI 情報が不足している

- 根拠:
  - `docs/requirements.md`
    - FR-013 同一名称の候補を登録できる
    - FR-014 同一名称の候補は名称ではなく内部 ID で区別する
  - `src/ui/RouletteApp.tsx`
    - 候補一覧表示は候補名と抽選状態のみ
    - 編集・削除ボタンの `aria-label` も候補名ベース
- 実装上の事実:
  - データ上は `id` で区別している
  - 画面上は重複候補を識別する補助情報がない
- 何が問題か:
  - 同名候補が複数あると、利用者がどの行を編集・削除するのか判断しづらい
  - 支援技術から見ても、操作対象の識別が弱い
- 想定される影響:
  - 誤編集、誤削除、運用上の混乱
  - FR-014 がデータ構造上のみ満たされ、利用者体験としては不足する
- 修正方針:
  - 一覧に識別用の補助情報を追加する
  - 例: 登録順、短縮 ID、作成時刻のいずれかを表示する
  - `aria-label` にも同じ識別子を含める
- 要件として明文化したい事項:
  - 同名候補が複数ある場合でも、利用者が個別に識別して操作できること

### 2-2. Medium: 候補名の長さ制約が UI 属性に寄っており、ロジックで保証されていない

- 根拠:
  - `src/ui/RouletteApp.tsx`
    - 入力欄に `maxLength={120}` が設定されている
  - `src/ui/useRouletteApp.ts`
    - 追加・編集時の検証は trim 後の空文字チェックのみ
- 実装上の事実:
  - 通常のブラウザ入力では 120 文字制限が働く
  - 追加・編集ロジック自体には上限制約がない
- 何が問題か:
  - UI 以外の入口が増えた場合や、将来別コンポーネントから同じロジックを使う場合に制約が外れる
  - 制約が UI とロジックで一貫していない
- 想定される影響:
  - 長大文字列の保存
  - `localStorage` 容量圧迫
  - 表示崩れや保守時の取りこぼし
- 修正方針:
  - 候補名バリデーションを hook または domain 側の共通関数へ寄せる
  - 追加・編集で同じ検証を使う
  - 文字数超過時のメッセージを定義する
- 要件として明文化したい事項:
  - 候補名の最大文字数と、超過時の扱い

### 2-3. Low: 抽選済み状態の復元テストが不足している

- 根拠:
  - `docs/requirements.md`
    - 再読み込み後も抽選済み状態が復元されることを求めている
  - `src/ui/RouletteApp.test.tsx`
    - 再読み込みテストは候補名と除外設定の復元を確認している
    - `drawn` 状態の復元までは確認していない
- 実装上の事実:
  - 保存データには `drawn` が含まれている
  - UI テストではその回帰防止が不足している
- 何が問題か:
  - 保存形式や読込処理の変更時に、抽選済み状態だけ壊れても CI で見逃す可能性がある
- 想定される影響:
  - 要件 FR-015 に対する回帰の検知漏れ
- 修正方針:
  - 抽選後に再マウントし、`抽選済み` 表示と抽選可能件数が維持されることを検証する

### 2-4. Low: スマートフォン対応の自動検証がない

- 根拠:
  - `docs/requirements.md`
    - PC とスマートフォンの主要モダンブラウザで操作できることを求めている
  - 現行テスト構成は `vitest` 中心で、ビューポート差異の実検証がない
  - `README.md` には手動確認項目がある
- 実装上の事実:
  - CSS はレスポンシブ対応を持つ
  - ただし自動検知の仕組みはない
- 何が問題か:
  - 画面変更時に、狭幅レイアウトの崩れを CI で検知できない
- 想定される影響:
  - モバイルでの操作不能や視認性低下の見逃し
- 修正方針:
  - Playwright 等の E2E を導入するか、少なくとも主要狭幅シナリオを自動化対象にする

## 4. テスト観点

### 追加したい観点

1. 抽選後に再読み込みしても `drawn` 状態と抽選対象件数が維持されること

3. 同名候補が複数あるときに、利用者が意図した行を識別して編集・削除できること
