# モバイル確認方針

- 対象リポジトリ: `tanaka03-sketch/roulette`
- 作成日: 2026-05-18
- 関連 Issue: `#31`
- 目的: スマートフォン幅での主要操作を、手動確認だけに頼らず段階的に自動検証へつなげる

## 1. 背景

現状のリポジトリでは、UI の主要フローは `vitest` と Testing Library で確認できるが、ビューポート差異によるレイアウト崩れや狭幅特有の操作性は自動検知できない。

一方で `README.md` には、モバイル確認の手動観点が整理されている。
そのため、まずは既存の手動観点を正式な確認基準として扱い、その後 Playwright による最小自動検証へ拡張する方針を採用する。

## 2. 採用方針

### Phase 1: 手動確認基準の正本化

- `README.md` のモバイル確認項目を、現行の確認基準として扱う
- 画面変更時はこの観点を最低限確認する
- 変更がモバイル表示に触れる場合、PR 説明に確認結果を残す

### Phase 2: 最小自動検証の導入

- Playwright を導入する
- スマートフォン幅の代表値として `390px` 前後を基準にする
- 主要 1 シナリオから始める
- スクリーンショット比較か、UI 要素の可視性確認のいずれかを使う

### Phase 3: CI 連携

- Playwright の狭幅確認を GitHub Actions に組み込む
- まずは pull request 時のみ実行して負荷を観察する
- 実行時間が許容範囲なら `main` push にも適用する

## 3. 自動検証の最小対象

最初に自動化する対象は、次の 1 シナリオを推奨する。

1. 候補を 2 件追加できる
2. 候補一覧と抽選パネルが横スクロールなしで表示される
3. 編集・削除ボタンが画面内で操作可能である
4. 抽選開始ボタン、抽選済み状態リセット、候補全削除が画面幅内に収まる
5. 長い候補名が結果表示からはみ出さない

## 4. Playwright で確認したい項目

- `390px` 幅でページが横スクロールしないこと
- 候補入力欄、候補一覧、抽選パネルが 1 カラムで読めること
- 同名候補の識別表示が狭幅でも読めること
- 編集・削除ボタンがタップ可能な大きさを保つこと
- 抽選結果の長い文字列が表示領域内で折り返されること

## 5. CI 組み込みの考え方

### 初期構成

- `ui-mobile` のような独立ジョブ名にする
- 既存の `typecheck` `test` `build` を壊さない位置に追加する
- pull request を先行対象にする

### 失敗時の扱い

- 初期は required にせず、安定後に必須化を検討する
- 失敗時はスクリーンショットかログで原因を追える構成にする

## 6. 追加で判断が必要になりやすい点

今後、実装段階では次の判断が発生しやすい。

### 1. Playwright をいつ導入するか

- すぐ導入する
- 次の UI 変更タイミングで導入する
- まずは手動運用を継続し、変更量が増えたら導入する

### 2. スクリーンショット比較を使うか

- 使う
- まずは可視性とレイアウト検査だけにする

### 3. CI で required にするか

- 初期から required にする
- 安定するまで optional にする

## 7. 現時点のおすすめ

- Playwright 導入は「次の UI 変更タイミング」で行う
- 初回はスクリーンショット比較ではなく、要素可視性とレイアウト検査を優先する
- CI では、まず optional 運用で安定させる

## 8. 完了条件との対応

| 完了条件 | この文書での扱い |
| --- | --- |
| モバイル確認の対象画面と観点が明文化されている | 対応済み |
| 少なくとも 1 本は狭幅回帰を捉える自動検証案がある | 対応済み |
| CI への組み込み方針が整理されている | 対応済み |
