## 推奨タスク一覧

### 1. 同名候補を識別できる UI 仕様を追加する

- 優先度: P1
- 種別: UX / Requirements
- 目的: 同名候補が並んでも利用者が個別に操作できるようにする
- 実装候補:
  - 候補一覧に登録順番号を表示する
  - 候補一覧に短縮 ID を表示する
  - 候補一覧に作成時刻を表示する
- 完了条件:
  - 同名候補が複数ある状態で、各候補を画面上で識別できる
  - 編集・削除ボタンの `aria-label` に識別子が含まれる
  - 要件書に識別仕様が明記されている
- おすすめ:
  - 初期版では「登録順番号」を採用する
- 理由:
  - 利用者に理解しやすく、実装も軽い

### 2. 候補名バリデーションを共通化する

- 優先度: P1
- 種別: Quality
- 目的: 追加・編集・将来拡張で同じ制約を保証する
- 実装候補:
  - `src/domain` に候補名検証関数を追加する
  - `useRouletteApp.ts` から共通関数を呼ぶ
- 完了条件:
  - 空文字と空白のみを拒否できる
  - 最大文字数をロジックで保証できる
  - 追加と編集で同じ検証を使う
  - 文字数超過時のメッセージが定義されている
- おすすめ:
  - 最大 120 文字制限を domain 側の共通関数で保証する

### 3. 抽選済み状態の復元テストを追加する

- 優先度: P2
- 種別: Testing
- 目的: 保存形式の変更で FR-015 を壊さないようにする
- 完了条件:
  - 抽選後の再読み込みで `抽選済み` 表示が復元される
  - 抽選対象件数も復元される
  - 既存の localStorage 復元テストと役割が重複しすぎない

### 4. スマートフォン対応の自動検証方針を追加する

- 優先度: P3
- 種別: Testing
- 目的: 狭幅 UI の回帰を自動で検知する
- 実装候補:
  - Playwright を導入する
  - 主要画面のスクリーンショット確認を追加する
  - まずは手動検証手順を docs に固定し、後で E2E 化する
- 完了条件:
  - モバイル確認の基準が明文化されている
  - 主要操作について少なくとも 1 つは自動検証がある
- おすすめ:
  - まずは手動観点の棚卸しを維持しつつ、次段で Playwright を導入する

## 着手順のおすすめ

1. 同名候補の識別仕様を決める
2. 候補名バリデーションを共通化する
3. 抽選済み状態の復元テストを追加する
4. モバイル自動検証を検討する

## 最小実装パッケージ案

最小の安全改善として、以下を 1 つの作業単位にまとめられる。

1. 要件書に同名候補の識別仕様を追記する
2. 候補名バリデーションを共通化する
3. 抽選済み復元テストを追加する

この 3 点までで、利用者影響のある懸念と回帰検知の弱点を一通り補える。

## 追加で仕様化したい事項

### 同名候補識別仕様

- 同名候補が複数ある場合、各候補には画面上で識別できる補助情報を表示する
- 初期版では登録順番号を表示対象とする
- 編集・削除操作にも同じ識別子を付与する

### 候補名制約

- 候補名は trim 後に 1 文字以上であること
- 候補名の最大文字数は 120 文字とする
- 制約超過時は画面上で明示的にエラー表示する

## 備考

- P1 の 2 項目は、コード修正と要件補強を同時に進めるのが効率的
- P2 は P1 の後に行うと、仕様変更後の正しい振る舞いをそのまま固定化しやすい
- P3 は今すぐの不具合よりも、将来の変更に備える意味合いが強い
